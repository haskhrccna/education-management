## iOS Password AutoFill gets wedged on register.password after an empty-submit attempt, defeating scripted typing (test-tooling finding, not an app bug)
- **Screen:** flows/auth (02-register-smoke)
- **Symptom:** on a *fresh* register screen, `tapOn: register.password` → `eraseText` → `inputText: "..."` reliably lands the typed text (confirmed via successful registration end-to-end). But if `register.password` was ever focused/blurred earlier on the *same screen instance* — even indirectly, e.g. via tapping submit with the form still empty and getting `register.error` — every subsequent attempt to type into it is silently desynced from React Native's controlled `TextInput` state: iOS's "Use Strong Password?" AutoFill sheet re-triggers on each focus, the field visually shows dots, but `handleRegister`'s client-side `!password` check still evaluates true (state stayed `''`). Reproduced this specific sequence 12/12 times across roughly 40 minutes of investigation (X-button dismiss + retap + erase + type, per-character typing, `pasteText` via clipboard, and accepting iOS's own "Fill Strong Password" suggestion were all tried as workarounds *within the same wedged screen instance* and all failed identically).
- **Root cause (best evidence):** iOS's per-field Password AutoFill "new password" heuristic state appears to latch to the screen/view instance once triggered, not just the field. React Navigation unmounting and remounting the screen (navigate to `login.screen` via `register.back-link`, then back to `register.screen` via `login.register-link`) resets it — the very first password fill+submit attempt on the *fresh* instance succeeds reliably (3/3 in verification runs after the fix, 5/5 total across this session once discovered).
- **Classification:** test-tooling/environment finding, **not an app bug**. A real user typing at normal human speed via the on-screen keyboard does not race iOS's AutoFill suggestion UI the way Maestro's fast scripted `inputText` does; this is specific to automated E2E typing speed colliding with a stateful system UI. Not fixed at the app level (would require disabling/tuning `textContentType`/AutoFill behavior on `register.password`, a product decision out of this task's scope).
- **Fix applied in this task:** `mobile/e2e/flows/auth/02-register-smoke.yaml` now navigates away from and back to `register.screen` (forcing a remount) between the empty-submit step (which the brief requires, to exercise `register.error`) and filling in real data, before entering the password. The password fill+submit is additionally wrapped in a small `retry:` block (3 attempts) as a safety margin for any residual on-device timing variance, but the remount alone accounts for the reliability gain.
- **Follow-up worth flagging:** any future E2E flow that needs to type into a *new-password-classified* field (this one, or `first-login.new-password`/`first-login.confirm-password`) right after that field's screen has already had earlier interaction should either remount the screen first or budget for this same class of flakiness.

## Date/time picker modal rows in student/appointments.tsx are not individually reachable by accessibility identifier (a11y bug, also breaks id-based e2e taps) (RESOLVED — Plan 1 findings fix-pass)
- **Severity:** Medium (accessibility — also a functional blocker for id-based test automation, though the underlying control works fine for a sighted/touch user)
- **Screen:** `mobile/app/student/appointments.tsx`, the date-picker and time-picker `Modal`s (`student-appointments.date-modal-sheet` / `time-modal-sheet`)
- **Steps:** From `student-appointments.screen`, tap `student-appointments.book` → `student-appointments.date-select` to open the date picker sheet (a `FlatList` of ~90 rendered Hijri-formatted date rows, each a `TouchableOpacity` with `testID={`student-appointments.date-option.${index}`}`).
- **Expected:** each row is individually reachable — both by Maestro's `id:`/`text:` selectors and, more importantly, by VoiceOver navigating item-by-item.
- **Actual:** `tapOn: { id: "student-appointments.date-option.0" }` fails with `Element not found`, even after `extendedWaitUntil` confirms the row is on-screen and the row is visibly rendered in a screenshot. Pulling the raw accessibility hierarchy (Maestro's screen-hierarchy JSON dump) shows the entire `date-modal-sheet` `Pressable` collapses into **one single accessibility node**, whose `accessibilityText` is all ~90 rows' date labels concatenated into one string (plus the close button and scrollbar description) — none of the individual `TouchableOpacity` rows appear as separate nodes in the tree. A raw coordinate tap at the first row's on-screen position (verified manually in the simulator, bypassing Maestro's element lookup) *does* select that date and close the sheet correctly — the control is functionally fine, it's specifically invisible to accessibility-tree-based navigation (Maestro's `id:`/`text:` selectors, and by the same mechanism, VoiceOver's swipe-to-next-element navigation).
- **Likely cause:** the two nested `Pressable`s wrapping the `FlatList` (`modalBackdrop` → `modalSheet`, both with an `onPress`) are each implicitly `accessible={true}` (RN's default for any pressable with `onPress`). On iOS, an accessible ancestor with accessible descendants that aren't themselves marked to stay separate typically gets its descendants "swallowed" into one element unless something (e.g. `accessibilityElementsHidden={false}` per child + explicit accessibility container handling) prevents it. `date-modal-close`, which sits as a direct sibling near the top rather than inside the `FlatList`, does still surface as its own node — consistent with the swallowing being specific to the `FlatList`'s deep nesting inside the accessible `modalSheet` Pressable.
- **Classification:** real app-level accessibility bug (WCAG AA row-level navigability) — FIXED. Added `accessible={false}` to both `date-modal-sheet` and `time-modal-sheet` Pressables (`mobile/app/student/appointments.tsx`), the same proven pattern already shipped for `admin/change-requests.tsx`'s row in Plan 1 Task 8. Verified live: `student-appointments.date-option.0`/`time-option.N` are now individually addressable by testID.
- **Test-flow workaround (superseded):** `02-appointments-smoke.yaml` previously dismissed both pickers via their `date-modal-close` / `time-modal-close` controls instead of selecting a specific row, since the row testIDs were unreachable. With the accessibility fix landed, the flow now selects `student-appointments.date-option.0` / `time-option.0` directly (closing the sheet as a side effect of the component's own `onPress`), re-verified passing end to end.

## `student-home.tsx` quick-action tiles intermittently navigate to the WRONG destination screen (RESOLVED — root-caused in the Plan 1 findings fix-pass, Task 4: it was never an app bug)
- **Severity (as originally logged):** Medium-High (wrong-destination navigation bug — affects multiple controls, not just one)
- **Screen:** `mobile/app/student/home.tsx`, the quick-actions grid (`quickActions[0..6]`, each a `TouchableOpacity` with `onPress={() => router.push(action.route as any)}` and `testID="student-home.quick-action.${index}"`)
- **Original steps / evidence (three independent reproductions across Plan 1's Tasks 5-6, different wrong destinations each time):**
  1. `quick-action.2` (grades) as the first navigation of a session → landed on `/student/appointments`.
  2. `quick-action.3` (reports), chained after other navigations → landed on `/student/grades`, and the wrong stack entry then corrupted a later `reports.back` tap.
  3. `quick-action.4` (revisions), first navigation of a fresh session → landed on `/student/appointments` again.
- **Root cause (found by re-testing against a genuinely fresh Metro `--clear` + a freshly erased iOS simulator, per this file's own standing recommendation, and isolating variables one at a time):** this is **not a defect in `student-home.tsx` or in expo-router** — the array/closure code was correct all along (confirmed again by direct reading). It is a defect in **Maestro's `scrollUntilVisible` command** when immediately followed by `tapOn`, specific to this Maestro/XCUITest driver version (2.8.0) on this iOS version (26.2):
  - A single manual coordinate tap (via the iOS Simulator control tool, bypassing Maestro entirely) at the exact same on-screen position as `quick-action.4` → **correct destination**, every time.
  - Maestro's own `tapOn: id:` → **correct destination**, every time, when the preceding scroll to bring the tile into view was performed *outside* Maestro (e.g., a manual swipe via the simulator tool).
  - Maestro's `scrollUntilVisible` immediately followed by `tapOn: id:` on the *same* element → **wrong destination, 100% of the time (4/4 attempts)**, always landing on `quick-action.0`'s destination (`/student/appointments`) specifically — never a random tile. Reproduced both as the very first navigation of a fresh session and chained after other navigations. Inserting a `waitForAnimationToEnd` between the scroll and the tap did not help.
  - The accessibility hierarchy itself was checked directly (`maestro hierarchy`) and confirmed correct, distinct, non-overlapping bounds for every `quick-action.N` element at the moment of failure — ruling out a duplicate-element or stale-bounds explanation.
- **`quick-action.2`/`.3` specifically — re-verified, not just inferred:** both sit above the fold on a fresh home-screen load (visible without any real scroll), so the `scrollUntilVisible`-then-`tapOn` race described above wouldn't be expected to apply to them (`scrollUntilVisible` should no-op when the target is already visible). To confirm rather than assume this, both tiles were independently re-tested against a fresh Metro/simulator using the **exact original pre-fix flow pattern** (`scrollUntilVisible` immediately followed by `tapOn`, matching what the original 8x `.2` reproduction and the Task 6 `.3` reproduction actually ran): `.2` passed cleanly 3/3, `.3` passed cleanly 3/3 — 6/6, zero failures. This rules out an ongoing, currently-reproducible defect for `.2`/`.3` under either the old or new flow pattern, but it does **not** retroactively prove what caused their original failures in Plan 1's dev session — since they don't need real scrolling, the specific `scrollUntilVisible` mechanism found for `.4`/`.5`/`.6` doesn't mechanistically explain them. The most likely explanation remains Plan 1's own original hypothesis (dev-session/Fast-Refresh corruption specific to that long-running Metro process), now indirectly supported by their clean re-test record, but this task did not — and could not — conclusively prove that negative.
- **Fix:** replace `scrollUntilVisible` with a plain `swipe` gesture before tapping any below-the-fold control on this screen. Verified live: 100% correct destinations (11/11) across every below-the-fold control (`quick-action.4`/`.5`/`.6`, `teacher-card`, `grades-view-all`, `mushaf-cta`) using `swipe` instead of `scrollUntilVisible`, both individually and as the full chained flow, then confirmed 3/3 clean end-to-end passes of the actual committed `01-home-smoke.yaml` with this fix applied.
- **Classification:** test-tooling defect (Maestro `scrollUntilVisible`) conclusively demonstrated for `.4`/`.5`/`.6`/`teacher-card`/`grades-view-all`/`mushaf-cta` (every below-the-fold control) — not an app bug, no `student-home.tsx` code changes were needed or made for these. `.2`/`.3` are RESOLVED in the practical sense that matters for this suite (both now pass reliably, 6/6, under both the old and new flow patterns, so full destination-assertion coverage was safely restored for them) but their *original* failure is only indirectly, not conclusively, attributed to the same root cause — flagging this distinction rather than overclaiming certainty Plan 1's evidence doesn't fully support.
- **Test-flow change:** `01-home-smoke.yaml` no longer uses `scrollUntilVisible` anywhere, and no longer uses the isolated-session/loose-assertion workaround. All 7 quick-action tiles (plus `teacher-card`, `grades-view-all`, `mushaf-cta`) now get full tap→assert-exact-destination→return coverage in a single continuous session, using `swipe` for anything below the fold.
- **Known follow-up not done in this task (out of Task 4's file scope):** `05-reports-smoke.yaml` and `06-revisions-smoke.yaml` (written during Plan 1's Task 6, before this root cause was known) still route around `quick-action.3`/`.4` via `openLink` deep links instead of tapping the tile directly, with comments describing the tap as unreliable. That workaround is now known to be unnecessary — a future task can restore direct tile-tap coverage in those two flows using the same `swipe`-based pattern, but doing so was not required to resolve this finding and was left alone to keep this task's diff scoped to `01-home-smoke.yaml`.

## `student-recordings.tsx`'s "record" button starts a REAL microphone recording on this simulator (mic permission persists across `clearState`)
- **Severity:** Low (test-environment finding, not an app bug — flagging for anyone else automating this screen)
- **Screen:** `mobile/app/student/recordings.tsx`
- **Steps:** Tap `student-recordings.record` on a simulator where microphone permission was granted in any prior session (even a much earlier, unrelated one).
- **Expected (per this task's coordinator resolution #3):** tapping record either shows a permission prompt or fails gracefully (the code's catch block has a specific "not available on simulator" message for exactly this case), without ever completing a live recording.
- **Actual:** on this task's simulator, `Audio.requestPermissionsAsync()` returned already-granted (no prompt shown, confirmed by three `tapOn ... optional: true` steps for "OK"/"Allow"/"While Using the App" all reporting `WARNED` — none of those dialogs appeared), and `Audio.Recording.createAsync(...)` succeeded — the recorder UI (`student-recordings.recording-banner`) appeared with a live incrementing timer (reached 0:16 elapsed in one run before being caught and canceled). - **Classification:** not an app bug — flagging as a test-environment/tooling note. `04-recordings-smoke.yaml` accounts for it: it asserts `student-recordings.recording-banner` becomes visible immediately after tapping record (proving the control works, permission-prompt-or-not) and taps `student-recordings.cancel-recording` on the very next step, before any meaningful recording duration accrues, per the coordinator's explicit "do not leave a real audio file artifact" requirement — `cancelRecording()` calls `stopAndUnloadAsync()` and discards the URI without ever calling `upload()`, so no file reaches the server.
- **Follow-up for whoever runs this simulator/flow next:** if a *fully* clean environment is needed (e.g. to test the actual permission-prompt UI), the microphone grant must be reset at the simulator level (`xcrun simctl privacy revoke microphone <bundle-id>` or a full simulator erase), not via Maestro's `clearState`.

- **Found by:** `admin/02-user-detail-smoke.yaml` (and `01-home-smoke.yaml`) during coordinator live-verify — navigating to user-detail (via `admin-analytics.teacher-row.0`) popped an `Error: Cannot read property 'user' of undefined` alert instead of rendering the screen.
- **Root cause:** `GET /admin/users/:id` returns `{ user, analytics }` **directly** as the response body (`admin.module.ts` `getUserById` → `return { body: result }`), NOT wrapped in a `{ data }` envelope like the LIST endpoint `GET /admin/users`. The screen read `const data = res.data?.data` (a nested `.data.data`), which was always `undefined`, then dereferenced `data.user` → TypeError. The screen was reachable in normal use (via `admin/analytics.tsx`'s teacher rows), so this was a live crash, not dead code.
- **Fix:** `res.data?.data` → `res.data` (with an explanatory comment). tsc clean; `admin/01`+`02` smoke flows pass live after the fix.
- **Note:** the inconsistency (single-resource endpoints un-enveloped, list endpoints enveloped as `{ data: [...] }` — see `admin/home.tsx`'s own comment) is a latent server-contract wart worth a broader audit, but out of Plan 2's scope; only the crashing consumer was fixed here.

## iOS Password AutoFill gets wedged on register.password after an empty-submit attempt, defeating scripted typing (test-tooling finding, not an app bug)
- **Screen:** flows/auth (02-register-smoke)
- **Symptom:** on a *fresh* register screen, `tapOn: register.password` → `eraseText` → `inputText: "..."` reliably lands the typed text (confirmed via successful registration end-to-end). But if `register.password` was ever focused/blurred earlier on the *same screen instance* — even indirectly, e.g. via tapping submit with the form still empty and getting `register.error` — every subsequent attempt to type into it is silently desynced from React Native's controlled `TextInput` state: iOS's "Use Strong Password?" AutoFill sheet re-triggers on each focus, the field visually shows dots, but `handleRegister`'s client-side `!password` check still evaluates true (state stayed `''`). Reproduced this specific sequence 12/12 times across roughly 40 minutes of investigation (X-button dismiss + retap + erase + type, per-character typing, `pasteText` via clipboard, and accepting iOS's own "Fill Strong Password" suggestion were all tried as workarounds *within the same wedged screen instance* and all failed identically).
- **Root cause (best evidence):** iOS's per-field Password AutoFill "new password" heuristic state appears to latch to the screen/view instance once triggered, not just the field. React Navigation unmounting and remounting the screen (navigate to `login.screen` via `register.back-link`, then back to `register.screen` via `login.register-link`) resets it — the very first password fill+submit attempt on the *fresh* instance succeeds reliably (3/3 in verification runs after the fix, 5/5 total across this session once discovered).
- **Classification:** test-tooling/environment finding, **not an app bug**. A real user typing at normal human speed via the on-screen keyboard does not race iOS's AutoFill suggestion UI the way Maestro's fast scripted `inputText` does; this is specific to automated E2E typing speed colliding with a stateful system UI. Not fixed at the app level (would require disabling/tuning `textContentType`/AutoFill behavior on `register.password`, a product decision out of this task's scope).
- **Fix applied in this task:** `mobile/e2e/flows/auth/02-register-smoke.yaml` now navigates away from and back to `register.screen` (forcing a remount) between the empty-submit step (which the brief requires, to exercise `register.error`) and filling in real data, before entering the password. The password fill+submit is additionally wrapped in a small `retry:` block (3 attempts) as a safety margin for any residual on-device timing variance, but the remount alone accounts for the reliability gain.
- **Follow-up worth flagging:** any future E2E flow that needs to type into a *new-password-classified* field (this one, or `first-login.new-password`/`first-login.confirm-password`) right after that field's screen has already had earlier interaction should either remount the screen first or budget for this same class of flakiness.

## Review fix-pass: text-tap replacement for the AutoFill-sheet point tap fails (point tap kept)
- **Screen:** flows/auth (02-register-smoke, 04-pending-approval-smoke)
- **Investigation:** the review brief asked to try replacing `tapOn: point: "91%, 61%"` (inside the `register.password` retry block) with a text-based tap on the "Use Strong Password?" sheet's actual close-button label, to avoid a raw coordinate. A standalone probe flow reproduced the exact repro sequence (empty-submit → remount → refocus `register.password`) and screenshotted the sheet: it is iOS's system "Use Strong Password?" popup with a circular "X" close control at the top-right and a "Fill Strong Password" primary button. The `X` control's on-screen position matches `91%, 61%` almost exactly (verified visually against the screenshot).
- **Result:** `tapOn: text: "Close", optional: true` was tried in place of the point tap. Maestro reported it as `WARNED` (no matching element — the system "X" control isn't exposed under a matchable text/accessibility label to Maestro's iOS driver). Following screenshots then showed the field displaying a stuck "Automatic Strong Password cover view text" banner instead of the typed password, and the subsequent registration submit failed to reach `pending-approval.screen` — the same class of desync/wedge failure this section already documents, just reproduced via a different trigger (a failed dismiss attempt instead of a second focus without remounting).
- **Conclusion:** the `point: "91%, 61%"` tap is kept as-is in both flows. Added to `COVERAGE.md`'s "Sanctioned text-selector exceptions" section with this evidence.

## Login success for a first-time ACTIVE user does not reach bottom-nav / home — routes to onboarding instead (not a bug, but breaks a Task 4 brief assumption)
- **Screen:** flows/auth (01-login-smoke, correct-credentials case)
- **Steps:** Log in as `ali@quran-review.com` / `Student1234!` (seeded ACTIVE student, `onboardingCompletedAt = null`) on a freshly reset E2E DB.
- **Expected (per Task 4 brief):** app lands on `/student/home`, asserting `bottom-nav.student-home` visible.
- **Actual:** `app/_layout.tsx`'s auth gate (`useEffect` around line 70-80, tagged "F5: first sign-in → role onboarding wizard") redirects any ACTIVE user with `onboardingCompletedAt == null` and role in `['student','teacher','parent']` to `/onboarding/${role}` instead, *before* the role-home screen is ever reached. `bottom-nav.student-home` is never rendered for a fresh onboarding-incomplete student. Completing the onboarding wizard doesn't reach `/student/home` either — `mobile/app/onboarding/student.tsx`'s `finish()` routes to `/student/mushaf` (a different, full-screen recording UI with no `BottomNav`), further decoupling "onboarding done" from "bottom nav visible."
- **Classification:** NOT an app bug — this is the intended F5 onboarding-gate feature working correctly. It is a **stale assumption in the Task 4 brief/Task 3 hand-off** (written before F5 landed on this branch, or not accounting for it): asserting `bottom-nav.student-home` (or Task 5's planned `student-home.screen`) right after a fresh seeded student's first login will not work without first driving the onboarding wizard (out of scope for Task 4 — no testIDs exist on `onboarding/*` screens, they weren't in Task 3's covered-screens list).
- **Fix applied in this task:** `mobile/e2e/flows/auth/01-login-smoke.yaml`'s final assertion was changed from `bottom-nav.student-home` to `notVisible: login.screen` + `visible: text "اهلاً بك في رحلة الحفظ"` (the onboarding welcome screen's copy) — still proves the credentials were accepted and the app navigated away from login, without depending on a destination this seeded user can't reach without further, out-of-scope onboarding automation.
- **Follow-up needed:** whoever does Task 5 (which plans to flip this assertion to `student-home.screen`) needs to either (a) seed a student with `onboardingCompletedAt` already stamped for auth-flow tests, or (b) add testIDs to the onboarding wizard and drive it to completion before asserting home, or (c) keep asserting on the onboarding screen for `ali` and use a *different*, onboarding-complete seeded user for any home-screen-specific flow.

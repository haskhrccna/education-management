## iOS Password AutoFill gets wedged on register.password after an empty-submit attempt, defeating scripted typing (test-tooling finding, not an app bug)
- **Screen:** flows/auth (02-register-smoke)
- **Symptom:** on a *fresh* register screen, `tapOn: register.password` → `eraseText` → `inputText: "..."` reliably lands the typed text (confirmed via successful registration end-to-end). But if `register.password` was ever focused/blurred earlier on the *same screen instance* — even indirectly, e.g. via tapping submit with the form still empty and getting `register.error` — every subsequent attempt to type into it is silently desynced from React Native's controlled `TextInput` state: iOS's "Use Strong Password?" AutoFill sheet re-triggers on each focus, the field visually shows dots, but `handleRegister`'s client-side `!password` check still evaluates true (state stayed `''`). Reproduced this specific sequence 12/12 times across roughly 40 minutes of investigation (X-button dismiss + retap + erase + type, per-character typing, `pasteText` via clipboard, and accepting iOS's own "Fill Strong Password" suggestion were all tried as workarounds *within the same wedged screen instance* and all failed identically).
- **Root cause (best evidence):** iOS's per-field Password AutoFill "new password" heuristic state appears to latch to the screen/view instance once triggered, not just the field. React Navigation unmounting and remounting the screen (navigate to `login.screen` via `register.back-link`, then back to `register.screen` via `login.register-link`) resets it — the very first password fill+submit attempt on the *fresh* instance succeeds reliably (3/3 in verification runs after the fix, 5/5 total across this session once discovered).
- **Classification:** test-tooling/environment finding, **not an app bug**. A real user typing at normal human speed via the on-screen keyboard does not race iOS's AutoFill suggestion UI the way Maestro's fast scripted `inputText` does; this is specific to automated E2E typing speed colliding with a stateful system UI. Not fixed at the app level (would require disabling/tuning `textContentType`/AutoFill behavior on `register.password`, a product decision out of this task's scope).
- **Fix applied in this task:** `mobile/e2e/flows/auth/02-register-smoke.yaml` now navigates away from and back to `register.screen` (forcing a remount) between the empty-submit step (which the brief requires, to exercise `register.error`) and filling in real data, before entering the password. The password fill+submit is additionally wrapped in a small `retry:` block (3 attempts) as a safety margin for any residual on-device timing variance, but the remount alone accounts for the reliability gain.
- **Follow-up worth flagging:** any future E2E flow that needs to type into a *new-password-classified* field (this one, or `first-login.new-password`/`first-login.confirm-password`) right after that field's screen has already had earlier interaction should either remount the screen first or budget for this same class of flakiness.

## Date/time picker modal rows in student/appointments.tsx are not individually reachable by accessibility identifier (a11y bug, also breaks id-based e2e taps)
- **Severity:** Medium (accessibility — also a functional blocker for id-based test automation, though the underlying control works fine for a sighted/touch user)
- **Screen:** `mobile/app/student/appointments.tsx`, the date-picker and time-picker `Modal`s (`student-appointments.date-modal-sheet` / `time-modal-sheet`)
- **Steps:** From `student-appointments.screen`, tap `student-appointments.book` → `student-appointments.date-select` to open the date picker sheet (a `FlatList` of ~90 rendered Hijri-formatted date rows, each a `TouchableOpacity` with `testID={`student-appointments.date-option.${index}`}`).
- **Expected:** each row is individually reachable — both by Maestro's `id:`/`text:` selectors and, more importantly, by VoiceOver navigating item-by-item.
- **Actual:** `tapOn: { id: "student-appointments.date-option.0" }` fails with `Element not found`, even after `extendedWaitUntil` confirms the row is on-screen and the row is visibly rendered in a screenshot. Pulling the raw accessibility hierarchy (Maestro's screen-hierarchy JSON dump) shows the entire `date-modal-sheet` `Pressable` collapses into **one single accessibility node**, whose `accessibilityText` is all ~90 rows' date labels concatenated into one string (plus the close button and scrollbar description) — none of the individual `TouchableOpacity` rows appear as separate nodes in the tree. A raw coordinate tap at the first row's on-screen position (verified manually in the simulator, bypassing Maestro's element lookup) *does* select that date and close the sheet correctly — the control is functionally fine, it's specifically invisible to accessibility-tree-based navigation (Maestro's `id:`/`text:` selectors, and by the same mechanism, VoiceOver's swipe-to-next-element navigation).
- **Likely cause:** the two nested `Pressable`s wrapping the `FlatList` (`modalBackdrop` → `modalSheet`, both with an `onPress`) are each implicitly `accessible={true}` (RN's default for any pressable with `onPress`). On iOS, an accessible ancestor with accessible descendants that aren't themselves marked to stay separate typically gets its descendants "swallowed" into one element unless something (e.g. `accessibilityElementsHidden={false}` per child + explicit accessibility container handling) prevents it. `date-modal-close`, which sits as a direct sibling near the top rather than inside the `FlatList`, does still surface as its own node — consistent with the swallowing being specific to the `FlatList`'s deep nesting inside the accessible `modalSheet` Pressable.
- **Classification:** real app-level accessibility bug (WCAG AA row-level navigability), not fixed in this task per scope (testIDs + flows only, `student-appointments.tsx`'s modal `Pressable`/`FlatList` structure is pre-existing code this task didn't author). Noted here for whoever next touches the date/time picker modals or does an accessibility pass on `student/appointments.tsx`.
- **Test-flow workaround (this task):** `02-appointments-smoke.yaml` dismisses both pickers via their already-reachable `date-modal-close` / `time-modal-close` controls instead of selecting a specific row — this still exercises the full open/close round trip deterministically without depending on the broken row-level exposure. `student-appointments.date-option.N` / `time-option.N` testIDs remain present in source (`check-testids.js` verifies this) but are not tapped by any flow; same "presence verified only" treatment as `student-appointments.submit` in `COVERAGE.md`.

## Standard API rate limiter (100 req / 15 min, not dev-scoped) trips during heavy E2E automation
- **Severity:** Low (operational/testability note, not a functional defect)
- **Where:** `packages/server/src/middleware/rate-limit.middleware.ts` — `standardLimiter` (`windowMs: 15*60*1000, max: 100`) is mounted on nearly every authenticated route (`appointments`, `grades`, `messages`, `notifications`, `memorization`, `mushaf`, etc. — see `app.ts:114-141`). Unlike `authLimiter`/`broadcastLimiter`/`passwordResetLimiter`, its `max` is a flat `100` regardless of `NODE_ENV` — the other limiters explicitly widen to `1000`/`1000`/`5→` in development.
- **Observed:** During this task's manual + Maestro-driven debugging of the quick-action navigation bug (below), the app surfaced a native alert reading "خطأ / Undeclared response status 429" from `student-appointments.tsx`'s `fetchAppointments()` catch block, after roughly a dozen rapid E2E-style navigations against the same long-running dev server process within one 15-minute window. Each home-screen mount alone fires 4 GET requests (`fetchProgress`, `fetchAppointments`, `fetchGrades`, `fetchMessages`), so a smoke suite that hops between screens rapidly (as this task's flows and any future ones will) can burn through the 100-request budget faster than a real user ever would in the same window.
- **Classification:** not fixed in this task (touching rate-limit config is out of scope for testIDs/flows) — likely intentional production behavior, but worth widening `standardLimiter` for `NODE_ENV=development` the same way the other four limiters already are, so long E2E sessions against a shared local dev server don't spuriously 429. Flagging for whoever next tunes `rate-limit.middleware.ts` or owns the E2E CI environment.

- **Severity:** Medium-High (wrong-destination navigation bug — affects multiple controls, not just one)
- **Screen:** `mobile/app/student/home.tsx`, the quick-actions grid (`quickActions[0..6]`, each a `TouchableOpacity` with `onPress={() => router.push(action.route as any)}` and `testID="student-home.quick-action.${index}"`)

From a fresh login, scroll to and tap `quick-action.2` (id `'grades'`, expected route `/student/grades`) as the very first navigation of the session → lands on **`/student/appointments`** instead (unambiguous: renders `"مواعيدي"`, `"احجز موعدك القادم"`, `"مواعيد قيد الانتظار"`, `"السجل"`). - **Classification:** real app bug, not fixed in this task per scope (testIDs + flows only). Flagging for whoever next touches `student/home.tsx`'s quick-actions grid or expo-router version/config — strongly recommend re-testing this against a **freshly restarted** Metro + simulator (not reused from a long dev session) as the first troubleshooting step, since this task cannot rule out dev-session-specific corruption vs. a genuine reproducible-in-production defect.

## `student-recordings.tsx`'s "record" button starts a REAL microphone recording on this simulator (mic permission persists across `clearState`)
- **Severity:** Low (test-environment finding, not an app bug — flagging for anyone else automating this screen)
- **Screen:** `mobile/app/student/recordings.tsx`
- **Steps:** Tap `student-recordings.record` on a simulator where microphone permission was granted in any prior session (even a much earlier, unrelated one).
- **Expected (per this task's coordinator resolution #3):** tapping record either shows a permission prompt or fails gracefully (the code's catch block has a specific "not available on simulator" message for exactly this case), without ever completing a live recording.
- **Actual:** on this task's simulator, `Audio.requestPermissionsAsync()` returned already-granted (no prompt shown, confirmed by three `tapOn ... optional: true` steps for "OK"/"Allow"/"While Using the App" all reporting `WARNED` — none of those dialogs appeared), and `Audio.Recording.createAsync(...)` succeeded — the recorder UI (`student-recordings.recording-banner`) appeared with a live incrementing timer (reached 0:16 elapsed in one run before being caught and canceled). This is because **iOS simulator microphone permission is OS/simulator-level state, not app state** — Maestro's `launchApp: clearState: true` (which clears the app's own storage/keychain) does **not** reset it, so a permission grant from any earlier manual test or a previous flow run persists indefinitely across "fresh" flow runs on the same simulator.
- **Classification:** not an app bug — flagging as a test-environment/tooling note. `04-recordings-smoke.yaml` accounts for it: it asserts `student-recordings.recording-banner` becomes visible immediately after tapping record (proving the control works, permission-prompt-or-not) and taps `student-recordings.cancel-recording` on the very next step, before any meaningful recording duration accrues, per the coordinator's explicit "do not leave a real audio file artifact" requirement — `cancelRecording()` calls `stopAndUnloadAsync()` and discards the URI without ever calling `upload()`, so no file reaches the server.
- **Follow-up for whoever runs this simulator/flow next:** if a *fully* clean environment is needed (e.g. to test the actual permission-prompt UI), the microphone grant must be reset at the simulator level (`xcrun simctl privacy revoke microphone <bundle-id>` or a full simulator erase), not via Maestro's `clearState`.

## Task 9: `grade-form.tsx`'s numeric-keypad score input has no dismiss control, and stays open to absorb later taps as its own keypad presses
- **Severity:** Medium (test-tooling finding, not an app bug — but it silently corrupts submitted data if not accounted for, so worth documenting clearly for anyone else automating this screen)
- **Screen:** `mobile/app/teacher/grade-form.tsx`, the score `TextInput` (`grade-form.grade-input`, `keyboardType="numeric"`)
- **Steps:** From `grade-form.screen`, tap `grade-form.grade-input`, type a value (e.g. `"A-"`), then — without dismissing the keyboard — scroll to and tap a control further down the form (`grade-form.type-chip.0`, then `grade-form.submit`).
- **Expected:** the taps land on the intended controls; submitting produces a grade record with exactly the typed value.
- **Actual:** two consecutive live runs showed the score field's value corrupted to `"A-0"` (an extra `"0"` character) after the later taps, and a DB query (`SELECT ... FROM grades WHERE ...`) confirmed **no new grade row was created at all** — the "submit" tap never reached the real button. Screenshots from both failures show the iOS numeric keypad still fully open and covering roughly the bottom 45% of the screen at the moment of failure, with its own `"0"` key highlighted/pressed.
- **Root cause:** `keyboardType="numeric"` on iOS maps to a keypad with no Done/Return key and no toolbar — there is no in-keyboard way to dismiss it, and the app adds no `KeyboardAvoidingView`, custom "Done" accessory, or `Keyboard.dismiss()` call anywhere in this screen. Maestro computes tap coordinates from the React Native view hierarchy's layout, which has no knowledge of the native iOS keyboard overlay sitting on top of (and physically intercepting touches within) that same screen region — so a `tapOn: id: ...` for an element that IS present and IS within the full screen bounds can still land on the keyboard instead, if the keyboard happens to be covering that exact point at tap time.
- **Classification:** test-tooling/environment finding, not an app bug in the strict sense (a real user typing at normal speed, seeing the keypad on screen, would naturally tap somewhere else on the visible UI to dismiss it rather than "trust" an occluded control) — but it is adjacent to a genuine UX gap worth flagging: this screen has no way at all to dismiss the numeric keypad once focused (no Done button, no tap-outside affordance beyond React Native's default `keyboardShouldPersistTaps="handled"` behavior on unhandled taps), which a real user would also find awkward.
- **Fix applied (this task):** added `testID="grade-form.header"` to the header's non-touchable `View` (source-level, `grade-form.tsx`) as a reliable, scroll-to-and-tap dismiss target. Relies on `keyboardShouldPersistTaps="handled"` (already set on the form's `ScrollView`): a tap that is NOT absorbed by a touchable child dismisses the keyboard. `03-grade-visibility.yaml` scrolls UP to `grade-form.header` and taps it (by testID, not a blind coordinate) immediately after typing the score and before any further scrolling/tapping. A first attempt using a raw `point: "50%, 5%"` tap (after scrolling `grade-form.student-select.0` into view) failed identically — `scrollUntilVisible` stops as soon as its target meets the visibility threshold, which left the (touchable) student chip itself near that same coordinate, so the "unhandled tap" dismiss never fired.
- **Follow-up worth flagging:** any future flow that types into a `keyboardType="numeric"`/`"decimal-pad"` field on this app should budget for the same class of issue — check whether the screen has a `KeyboardAvoidingView`/Done-button/dismiss affordance before assuming later taps will land correctly, and prefer a definite non-touchable testID'd dismiss target over a raw coordinate guess.
